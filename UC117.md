## Part 1 – Use Case Description

### 1.1 Business Context
Teams ship code continuously and want to release features gradually, turn them off quickly when something breaks, and change configuration without redeploying. Flags kept in code or config files are hard to audit, hard to roll back and easy to change without review. A central console gives control, safety and history.

### 1.2 Problem Statement
Build a feature-flag and configuration service with an admin console. Flags have per-environment values and targeting rules, including percentage rollout and attribute-based rules. Changes need approval, are versioned with author and reason, and can be rolled back in one click. A client endpoint evaluates flags quickly and supports caching. This application contains no AI features.

### 1.3 Target Users
| User | What they need |
|---|---|
| Developer | Create flags and propose changes to values and rules |
| Approver | Review and approve or reject proposed changes before they go live |
| Admin | Manage environments, API keys and users, and perform rollbacks |
| Client application | A fast, authenticated endpoint to fetch or evaluate flags |

### 1.4 Core Capabilities
1. **Flag management.** Create, edit and archive flags with a key, description and type (boolean, string or number).
2. **Environments.** Each flag has its own value and on/off state per environment (for example dev, test, prod).
3. **Targeting rules.** Percentage rollout using stable hashing, and attribute rules (for example country equals X, plan in a list), evaluated in order.
4. **Approval workflow.** Changes to protected environments are submitted, reviewed and approved before they take effect.
5. **History and rollback.** Every change is a new version with author and reason, and any earlier version can be restored in one click.
6. **Evaluation endpoint.** A client sends a user context and receives the flag result, or fetches a full config snapshot.
7. **Caching.** The snapshot endpoint returns an ETag so clients can poll efficiently and receive 304 when nothing changed.

### 1.5 Technology Stack
| Layer | Service |
|---|---|
| API | ASP.NET Core Minimal API with EF Core |
| Authentication | ASP.NET Core Identity with JWT (developer, approver, admin roles); API key per environment for evaluation |
| UI | Angular or React with TypeScript (candidate's choice) |
| Storage | Azure SQL Database (flags, rules, change history) |
| Hosting | Azure App Service |

### 1.6 Non-Functional Requirements
| NFR | Target |
|---|---|
| Performance | Flag evaluation responds in under 50 ms |
| Determinism | The same user always gets the same percentage-rollout result |
| Traceability | Every change is versioned with author and reason |
| Security | The evaluation endpoint is authenticated by an API key per environment |

### 1.7 Expected Outcomes
- Flags are managed per environment.
- Percentage and attribute targeting works.
- Change history exists, with rollback.
- The evaluation endpoint is cached and efficient to poll.

## Part 2 – What Is Expected from the Developer / Candidate

### 2.1 What You Must Build
Deliver a working application, not slides or a design document only. AI and LLM features are out of scope. At minimum:

| # | Deliverable | Required |
|---|---|---|
| 1 | Data model and EF Core migrations: flags, environments, per-environment values, rules, versions, API keys | Must |
| 2 | Flag CRUD API with validation and unique flag keys | Must |
| 3 | JWT login with developer, approver and admin roles, enforced on the server | Must |
| 4 | Admin console: flag list, environment toggles and rule editor | Must |
| 5 | Evaluation endpoint with API key per environment and rule evaluation in order | Must |
| 6 | Percentage rollout using stable hashing of flag key plus user id | Must |
| 7 | Attribute rules with at least equals, in-list and not-equals operators | Must |
| 8 | Versioned change history with author and reason, and one-click rollback | Must |
| 9 | Approval workflow: developers cannot approve their own change | Should |
| 10 | Snapshot endpoint with ETag and 304 support | Should |
| 11 | Automated tests: service tests for rollout and rule evaluation, and at least one API test | Must |
| 12 | A short README: how to run, design choices, known limitations | Must |

"Must" items carry the main weight. "Should" items separate a strong submission from a passing one.

- **Frontend choice.** Choose either Angular or React (with TypeScript) and state your choice in the README.

### 2.2 Engineering Expectations
- **Data model.** Use EF Core migrations. Keep flag definition, environment state and version history in separate tables, with clear keys and indexes on flag key and environment.
- **Concurrency control.** Use a row version token so two people editing the same flag cannot silently overwrite each other. Return 409 on conflict and show it in the UI.
- **Transactions.** A change, its new version row and its approval status must be saved together.
- **Authentication and authorization.** Enforce roles in the API. Developers propose, approvers approve, admins manage keys and roll back. The approver must not be the author. Evaluation uses an API key, not a user JWT. Store only hashed API keys.
- **Input validation.** Validate flag keys, rollout percentages (0 to 100), rule operators and value types.
- **Stable hashing.** Use a deterministic hash (not `string.GetHashCode`, which varies between processes) so the same user gets the same bucket on every instance.
- **API design.** Use REST status codes, DTOs, paged flag lists, and ETag with If-None-Match on the snapshot.
- **Frontend state.** Keep flags, filters and pending changes in a central state store (NgRx in Angular, or Redux Toolkit in React). Show loading, empty and error states, and confirm before rollback.
- **Error handling.** Return a consistent error shape. An evaluation request for an unknown flag returns a defined default, not an unhandled exception.
- **Configuration and secrets.** Use environment variables or user secrets. Do not commit keys.
- **Code quality.** Separate endpoints, services and data access, and add the tests listed above.

### 2.3 Data and Inputs
Seed sample data yourself: a few environments, about ten flags of different types, and a mix of rules (a 20 percent rollout, a country rule, a plan rule). Use fake user ids and attributes for evaluation. Do not use real personal data.

### 2.4 What to Demonstrate at the End
Prepare a short walkthrough of about 10 minutes covering:
1. Creating a flag and toggling it per environment.
2. Adding a percentage rollout and an attribute rule.
3. Evaluating several user ids to show stable, repeatable results.
4. Proposing a change, approving it as a different user, and seeing it go live.
5. Viewing history and rolling back a version.
6. The ETag behaviour (200 then 304) and a rejected request with a wrong API key.

### 2.5 How Your Work Will Be Evaluated
| Area | What the panel looks for |
|---|---|
| Functional completeness | Flags, rules, approval, history, rollback and evaluation work end to end |
| Data model and business rules | Correct versioning, stable rollout, correct rule order, conflict handling |
| Security | Server-side role checks, no self-approval, hashed API keys, no hardcoded secrets |
| API and code quality | Clean layering, DTOs, status codes, ETag, tests present |
| Frontend UX | Clear toggles, usable rule editor, visible conflict and error states |
| NFR adherence | Evaluation under 50 ms, deterministic results, versioned changes |
| Communication | Clear demo, honest limits, reasonable trade-off decisions |

### 2.6 Out of Scope
- Any AI or LLM features, including automated rollout recommendations
- SSO tenant setup or external identity providers
- Real email or chat notification providers; use stubs
- Client SDK packages for multiple languages (a documented HTTP endpoint is enough)
- Experimentation or statistical analysis of rollouts

### 2.7 Common Pitfalls
- Using `string.GetHashCode` for bucketing, so users change buckets after a restart or on another instance.
- Last write wins with no concurrency check on flag edits.
- Hiding the approve button in the UI while the approve endpoint accepts anyone.
- Letting an author approve their own change.
- Storing API keys in plain text.
- Rollback that edits history instead of creating a new version.
- Evaluating rules in an undefined order, or querying the database several times per evaluation and missing the 50 ms target.
